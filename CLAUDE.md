# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ระบบบริหารข้อมูลความเสี่ยงและความเปราะบางของชุมชน (community risk & vulnerability data management system) for อำเภอเมือง, จังหวัดมหาสารคาม. A Laravel 12 + Inertia.js v2 + Vue 3 SPA, built on the official `laravel/vue-starter-kit`.

- Frontend: Vue 3 (`<script setup lang="ts">`), TypeScript, Tailwind CSS, shadcn-vue style UI components.
- Backend: Laravel 12, Inertia (server-driven routing, no separate REST/API layer for pages), Ziggy for route helpers in JS.
- Map: Leaflet (npm package, not CDN) — see `resources/js/pages/Welcome.vue` for the reference implementation (custom `L.divIcon` markers, per-risk `L.featureGroup` layers, tile-style toggle).
- Font: Anuphan everywhere (loaded via Google Fonts in `resources/views/app.blade.php`, set as `font-sans` in `tailwind.config.js` / `resources/css/app.css`). Icons: FontAwesome Free, installed as an npm package and imported in `resources/css/app.css` (not CDN).
- SPA behavior comes from Inertia itself — there is no `vue-router`. Navigation is server-routed (`routes/*.php` → `Inertia::render('PageName')`) but rendered client-side without full page reloads.

## Commands

```bash
composer install && npm install       # install deps
cp .env.example .env && php artisan key:generate

composer dev                          # run server + queue listener + pail logs + vite, concurrently (recommended for local dev)
php artisan serve                     # backend only
npm run dev                           # vite dev server only
npm run build                         # production build (also required before `npm run build:ssr`)

vendor/bin/pint                       # PHP formatting (run before committing PHP changes)
npm run format                        # Prettier (resources/)
npm run lint                          # ESLint --fix (resources/)

php artisan test                      # run all tests (or: vendor/bin/phpunit)
php artisan test --filter=test_name   # run a single test
php artisan test tests/Feature/DashboardTest.php
```

Tests are plain PHPUnit test classes under `tests/Feature` and `tests/Unit` (not Pest syntax, despite `tests/Pest.php` existing as an unused starter-kit leftover — `pestphp/pest-plugin` is not in `composer.json`). Tests run against in-memory SQLite (`phpunit.xml`); local dev DB is MySQL (`.env`, XAMPP).

CI (`.github/workflows/`) runs `vendor/bin/pint`, `npm run format`, `npm run lint` on push/PR (lint.yml), and `phpunit` + `npm run build` (tests.yml).

## Architecture

**Page routing**: `routes/web.php`, `routes/auth.php`, `routes/settings.php`, `routes/admin.php` define server routes that return `Inertia::render('PageName')`, resolving to `resources/js/pages/PageName.vue` (path relative to `pages/`, e.g. `Inertia::render('settings/Appearance')` → `resources/js/pages/settings/Appearance.vue`). There are no Blade views for actual pages — `resources/views/app.blade.php` is the single Inertia shell (fonts, `@vite`, `@inertia`), and `resources/views/example.blade.php` is a static HTML/JS mockup kept only as a design reference (it predates `Welcome.vue` and is not served by any route).

**`routes/admin.php`**: all back-office routes, under `['auth', 'verified']` plus `role:` gating by **module** (product decision 2026-10-29). There are three tiers. The **6 display pages** (`/dashboard` = เกี่ยวกับระบบ, `/risk-overview`, `/community-map`, `/risk-factors`, `/impact-recovery`, `/mcr2030-kpi`) are `role:admin,staff,member`, open to every account. The **จัดการข้อมูล** module (`/data-import`) is `role:admin,staff`. The **ตั้งค่าระบบ** module (`/users`, `/communities`, `/scoring-criteria`) is `role:admin`. See "Roles" below. `App\Http\Controllers\Admin\*` and `resources/js/pages/admin/*.vue` are the corresponding namespace/folder. Put new back-office pages there, gated by the module they belong to, rather than adding another top-level routes file. For a new admin page: add the route here, add the nav entry in `AdminLayout.vue`'s `navItems` (as a child of the right module: แดชบอร์ด, จัดการข้อมูล or ตั้งค่าระบบ), and use `AdminLayout` as the page's layout.

**Entry point**: `resources/js/app.ts` boots Inertia + Ziggy, resolves pages via `resolvePageComponent` globbing `./pages/**/*.vue`.

**Auth/session props**: `app/Http/Middleware/HandleInertiaRequests.php` shares props (e.g. `auth.user`) available in every page via `$page.props` / `usePage()`. It also shares `flash.status` and `flash.error` (the session `status`/`error` flashes). Admin controllers set them with `back()->with('status', 'ข้อความ…')` for success, or `back()->with('error', …)` when an action is refused. `AdminLayout.vue` shows them as a top-right toast, green or red. For refusals, use `error` rather than `abort(403)`, so the admin isn't dumped onto an error page. AdminLayout listens to `router.on('success')` instead of watching the prop, so two identical messages in a row still each show. Every admin page gets this toast automatically, so don't add page-local toasts.

**Auth policy — self-registration is disabled.** `routes/auth.php` has no `register` routes (removed intentionally); `RegisteredUserController` and `pages/auth/Register.vue` still exist in the codebase but are unrouted/unlinked. Accounts are provisioned by an admin via `php artisan db:seed` (`database/seeders/DatabaseSeeder.php` seeds `test@example.com` / `password` as `member`, plus the real admin account below — replace/remove the test account before any real deployment). Login/logout/password-reset/email-verification all work normally through the standard Laravel session guard. `Welcome.vue`'s login modal (email+password, "ลืมรหัสผ่าน?" switches the same modal to a password-reset-request form) posts to these same routes via Inertia's `useForm` — it is a real auth client, not a mock. The modal's "เข้าระบบด้วยบัญชี @gmail" button is intentionally disabled (`disabled`, no handler) — Google/Socialite login was explicitly descoped, not forgotten; wiring it up needs `composer require laravel/socialite`, real Google OAuth credentials in `.env`, and a decision on whether Google sign-in may auto-create new accounts (it should probably match the same "no self-service account creation" policy as password login, but that's a product decision to confirm, not assume).

**Roles**: `App\Enums\UserRole` (`admin` | `staff` | `member`), stored as a plain `string` column on `users` (`role`, default `member`), cast to the enum on the `User` model. Route-level gating uses the `role:` middleware alias (`App\Http\Middleware\EnsureUserHasRole`, registered in `bootstrap/app.php`) — e.g. `Route::...->middleware(['auth', 'verified', 'role:admin,staff'])`. `User::canAccessAdminPanel()` is the **single source of truth** for "can this user reach `/dashboard`" (all three roles as of the current permission model — see the per-menu breakdown below) — both `AuthenticatedSessionController::store()` (post-login redirect) and `AppServiceProvider::boot()` (`RedirectIfAuthenticated::redirectUsing(...)`, for the `guest` middleware's "already logged in" redirect on `/login`) call it, and must keep calling it rather than re-deriving the role check inline. **This split was a real bug once**: Laravel's default `guest`-middleware redirect always targets `route('dashboard')` if it exists, with no regard for role — an already-logged-in member hitting `/login` (e.g. to switch accounts) got bounced straight into a 403 with their new credentials never even processed, and no visible way to log out to recover, since `Welcome.vue`'s header didn't show auth state at all. Both are now fixed (role-aware redirect + `Welcome.vue` shows a user chip/logout when `auth.user` is set) — if you add another role-gated route, ask whether the same two spots need updating. Seeded accounts: `test@example.com` / `password` (member), `wongnarin.s@msu.ac.th` / `w123` (admin, real credentials requested by the project owner — rotate before production).

**Per-menu permission matrix** (current product decision, 2026-10-29, distinct from `canAccessAdminPanel()` which only gates the panel itself). Access is split **by module, not by page**:
- **`admin`** gets every menu.
- **`staff`** gets the 6 display pages plus the `จัดการข้อมูล` module (`นำเข้าข้อมูล`). Staff can't reach anything under `ตั้งค่าระบบ`, but still see it as an inert placeholder.
- **`member`** gets the 6 display pages only. `จัดการข้อมูล` is hidden, and `ตั้งค่าระบบ` is an inert placeholder.

`AdminLayout.vue`'s `navItems` hides entries the current user can't reach, rather than showing a dead link that 403s. `routes/admin.php`'s `role:` middleware is the actual enforcement, so keep both in sync. Within the import module, *which sheets* a staff user may import is a separate per-user grant (see กลุ่มงาน below).

**Backend rebuild (from 2026-10-29)**: after the project owner's talk with the client, the real backend is being built **one menu at a time, owner-led, using only settled data** — don't jump ahead to other menus or convert mock pages to the DB unprompted. `communities` is the first real domain table; everything else is still mock.

**`จัดการชุมชน`** (`/communities`, `role:admin`, child of `ตั้งค่าระบบ`): `App\Http\Controllers\Admin\CommunityManagementController` + `CommunityRequest` + `resources/js/pages/admin/Communities.vue`, model `App\Models\Community`, table `communities` (`code` unique, `name` unique). Fields are deliberately just **code + name** (product decision). `code` is the client's own `COMMUNITY_ID` (`R001`–`R032`, validated `^R\d{3}$`) from `data_input_mcr2030_v4.xlsx` — it is the join key for future imports, and its numbering is **not** the same order as `mahasarakham.ts`'s local `id` (e.g. ตักศิลา 1 = `R031` but local id 1). `name` is stored **without** the "ชุมชน" prefix, exactly as in the client file (the request strips a typed prefix; the UI prepends it for display). Official spelling is **ตักศิลา** (not ตักสิลา). The page shows names **without** the prefix everywhere (product decision — don't re-add "ชุมชน" in display). Layout (product decision): 3 side-by-side tables × 15 rows per page (45/page, so all 32 fit on one page; pagination only appears past 45), columns รหัส/ชื่อชุมชน/ขอบเขตแผนที่ only; clicking a row opens the edit modal, which is also where delete lives (no per-row action column). **`code` is immutable after creation** (product decision, to prevent mistakes on the import join key): the edit modal shows it as a gray read-only box, and `CommunityRequest` only validates/returns `code` on store, so update ignores any submitted code — a wrong code is fixed by deleting and re-adding. The create/edit modal's header bar is solid `bg-blue-600` with white text. That is the exact class of AdminLayout's active/focused menu item, which is the color the owner asked for. Don't confuse it with the sidebar background `bg-slate-900`: that was tried once by mistake and rejected. Delete goes through `components/admin/ConfirmDialog.vue`, a styled confirm dialog stacked above the modal, not `window.confirm()`. Reuse it for any other admin delete confirmation (`Users.vue` still uses plain `confirm()`). The create modal has a collapsible "ขั้นตอนการเพิ่มชุมชน" `<details>` listing the 3-step add-boundary process. Seeded by `CommunitySeeder` (idempotent, called from `DatabaseSeeder`). **Map boundaries/coordinates are not in the DB** (option chosen 2026-10-29): they stay in `communityBoundaries.ts`/`mahasarakham.ts`, which now carry a `code` per community so `Communities.vue` can show a read-only "ขอบเขตแผนที่ มี/ไม่มี" column. A community added through this page has no map polygon until a developer adds it to those two files (and the public/dashboard maps still read the `.ts` list, not the DB). Delete is unrestricted for now because nothing references `communities` yet — once assessment/event tables exist, add a restricting FK/guard.

**User management** (`/users`, admin-only): `App\Http\Controllers\Admin\UserManagementController` + `resources/js/pages/admin/Users.vue`. Since self-registration is disabled, this is the only way new accounts get created — plain CRUD (no pagination yet; revisit if the user list grows large). UI (2026-10-29, same pattern as จัดการชุมชน): search + role filter chips with counts, row click opens the edit modal (blue `bg-blue-600` header, delete inside the modal via `ConfirmDialog`, no delete button on your own account).

**กลุ่มงาน / import permissions** (product decision 2026-10-29): `App\Enums\WorkGroup` = the **8 กลุ่มงาน, one per input sheet** of `data_input_mcr2030_v4.xlsx`. They are fixed in code and not admin-editable. Each case has `label()` (display) and `sheetName()` (the trimmed real sheet name, since `งาน ปภ1 ` has a trailing space). Renamed labels: งาน ปภ1 → งานป้องกันภัย, งาน ปภ_เหตุการณ์ → งานป้องกันภัยเหตุการณ์, KPI_เพิ่มเติมได้ → งาน KPI. The rest use their sheet names.

The admin ticks which groups a user may import, and one user can have several. These are stored in `users.work_groups` (JSON, `AsEnumCollection`). **Role interplay:**
- `admin` imports every group implicitly. Nothing is stored.
- `staff` **must** have ≥1 group. This is validated in `Concerns\ValidatesWorkGroups`.
- `member` imports none. The section is hidden and the stored list is cleared.

`User::canImport(WorkGroup)` is the single source of truth for that check. **It isn't enforced anywhere yet**, because นำเข้าข้อมูล is still mock. When that menu becomes real, it must use `canImport()` per sheet rather than re-deriving the check.

Guard failures no longer render a 403 page:
- Demoting the last admin throws a `ValidationException` on `role`, so it shows as a form error.
- Deleting yourself or the last admin returns `back()->with('error', …)`, which shows as a red toast.

`lastAdminViolation()` returns the message, or `null` if the action is allowed. If you touch this controller, keep both guards — they protect against different lockout scenarios (see the tests in `tests/Feature/Admin/UserManagementTest.php` for why the "delete" guard and "demote" guard can't be collapsed into one check: destroy always requires the actor to already be an admin, so "delete the last admin" and "delete yourself" overlap in practice, but demotion doesn't have that overlap).

**Locale**: `APP_LOCALE=th` (fallback `en`) — `lang/th/auth.php` translates the auth-guard error strings (`auth.failed`, `auth.throttle`) since the whole UI is Thai. `lang/th/validation.php` (added 2026-10-29) translates the common validation rules plus `attributes` (ชื่อ/อีเมล/รหัสผ่าน/สิทธิ์การใช้งาน/…). It is partial on purpose: any rule not in it falls back to English per key, so add the key when a new rule starts showing in the UI. Form-specific wording still belongs in that FormRequest's `messages()`. Extend `lang/th/*.php` as more server-side user-facing strings come up rather than leaving them in English.

**Layouts**: `resources/js/layouts/` (`AppLayout`, `AppHeaderLayout`, `AppSidebarLayout`, `AuthLayout` and variants) wrap authenticated/settings pages. Full-screen/standalone pages like `Welcome.vue` intentionally render with no layout wrapper.

**UI components**: `resources/js/components/ui/*` are shadcn-vue primitives (Button, Dialog, Sidebar, etc.) — see `components.json` for the shadcn-vue config (aliases, Tailwind base color `neutral`). Don't hand-roll a component if an equivalent already exists there.

**Map pages** (pattern established in `Welcome.vue`): keep the Leaflet `L.Map` instance and layer/tile-layer objects as plain module-scope variables (`let`), *not* `ref`/`reactive` — Leaflet manages its own internal mutable state and wrapping it in Vue's reactivity is unnecessary and can misbehave. Always `map.remove()` in `onUnmounted` since Inertia navigation mounts/unmounts page components without a full browser reload, and Leaflet throws if you re-`L.map()` the same container without cleanup.

**Body-level page styles**: pages needing full-viewport/no-scroll layouts (like `Welcome.vue`) toggle a class on `document.body` in `onMounted`/`onUnmounted` rather than setting it globally in CSS, since multiple Inertia pages share one `<body>` across navigations.

**Sourcing real geodata** (pattern established in `Welcome.vue`): don't invent coordinates/boundaries and present them as real. Administrative boundary polygons (province/district/municipality) can be pulled live and legitimately via Nominatim (`https://nominatim.openstreetmap.org/search?...&format=geojson&polygon_geojson=1`, © OpenStreetMap contributors, ODbL — attribute it). Official place/community names and counts for this municipality come from `data.mkm.go.th` (เทศบาลเมืองมหาสารคาม's own open-data portal), not Wikipedia (which was found outdated: 30 vs. the current official 32 ชุมชน). Sub-municipal "ชุมชน"-level boundaries are not published anywhere as open geodata; the project owner has since supplied a real digitized shapefile for these (see the community-area zones note below) — when real names/boundaries exist but per-point coordinates or per-community area polygons don't, generate an approximation from what real data *does* exist and say so both in a code comment and somewhere user-visible, rather than fabricating precision that doesn't exist. This is now the exception rather than the norm for community-area shading specifically, since real polygons exist — but the general principle (don't fabricate precision) still applies to any other geodata gap that comes up.

**Shared community/boundary data**: `resources/js/data/mahasarakham.ts` is the single source of truth for `MAP_CENTER`, `MUNICIPALITY_BOUNDARY`, `riskColors`, `riskNameTH`, and the 32-entry `communities` array (see the "Sourcing real geodata" note above for what's real vs. placeholder in there). `Welcome.vue` imports from it (and so should every rebuilt admin map page) — **don't re-declare this data in a new page; import it**, so the ~150-point boundary polygon and community list stay in exactly one place.

**Real community-area zones** (`resources/js/data/communityBoundaries.ts` + `resources/js/data/communityZones.ts`, used by `Welcome.vue`'s public map. The admin pages that also used them were deleted in the 2026-10-29 reset; new display pages should import them again rather than re-deriving zones): as of 2026-09-22 these are **real digitized boundaries**, not an approximation. The project owner supplied an ESRI Shapefile (`ขอบเขตชุมชน32เขต.shp` + sidecars, originally in `public/place/`, EPSG:4326/WGS84 — see [[reference_community_boundary_shapefile]] in memory for the extraction details) covering all 32 communities; `communityBoundaries.ts` hardcodes its ring coordinates (converted from the shapefile's `[lng, lat]` GeoJSON order to this codebase's `[lat, lng]` convention), matched to `mahasarakham.ts`'s `id` **by community name** — the shapefile's own `ID` attribute (0–31) is an unrelated numbering scheme from the source GIS system and must never be used for this join. One community, ชุมชนนาควิชัย 3 (id 9), has two disjoint polygon parts in the source data (an exclave); `CommunityZone.polygon` is therefore typed `[number, number][][]` (an array of rings, almost always length 1) rather than a single flat ring, and gets passed straight to `L.polygon()`, which fills every ring independently under the even-odd rule — no special-casing needed for the multi-part case, but any code touching `.polygon` must guard on `.length === 0` (no boundary data) rather than assuming a single ring's point count. `communityZones.ts` itself just joins this real data with each community's `activeRisk`/name/lat/lng from `mahasarakham.ts` — `Welcome.vue` still colors zones by hazard type (`riskColors[com.activeRisk]`) (the deleted admin `Dashboard.vue` used to color by computed HEVC risk level instead — pick per page when rebuilding); only the shapes underneath it are now real. **This replaced an earlier Voronoi-diagram approximation** (`d3-delaunay` cells over the 32 community center points, clipped to `MUNICIPALITY_BOUNDARY` via `polygon-clipping`) that existed only as a stand-in while waiting for the real shapefile — that generation logic, and the `d3-delaunay`/`polygon-clipping` npm dependencies it needed, are gone now; the amber "ขอบเขตพื้นที่ชุมชนเป็นการประมาณชั่วคราว" disclaimers that used to appear near the map heading, in a floating chip on the public homepage, and in every zone popup were removed from all 5 consuming pages for the same reason — don't re-add them, and don't assume they're still there if grepping old context. If the shapefile ever needs re-extracting (a correction from the data provider, a new community, etc.), the shapefile itself is kept for provenance per the project owner's choice — ask where it's currently stored (it started in `public/place/` for dev convenience, see the public-webroot cleanup reminder in memory) rather than assuming it's gone. **`mahasarakham.ts`'s `communities[].lat/lng` had to be recomputed at the same time** — they used to be arbitrary placeholder points that only lined up with zones by construction (the old Voronoi cells were generated *from* those exact points); once real, independently-sourced polygons replaced the zones, every one of the 32 old points fell outside its own real polygon (verified: 32/32 mismatched, often landing inside a distant unrelated community's polygon instead — a real bug this project owner caught by eye in a screenshot, see `mahasarakham.ts`'s comment above the `communities` array for the full story and how to recompute if `communityBoundaries.ts` is ever regenerated).

**Fading Leaflet filter toggles** (`resources/js/lib/leafletFade.ts`, used by both `Welcome.vue`'s risk-type radio filter): Leaflet has no built-in transition for vector layers (`L.FeatureGroup`/`L.Polygon`/`L.Marker`) the way raster tile layers do, so `fadeInGroup()`/`fadeOutGroup()` reach into each layer's DOM element (`getElement()` where public, the private-but-stable `_path` for `Path`-based layers using the default SVG renderer) and drive a plain CSS `opacity` transition before actually calling `map.removeLayer()`. Reuse these two functions for any new toggleable map layer rather than reintroducing instant add/remove or a second animation implementation.

**Admin panel** (`resources/js/layouts/AdminLayout.vue`) is a bespoke dark-sidebar shell, not the shadcn `AppSidebarLayout`: it has a different visual language and is built custom like `Welcome.vue`. As of 2026-10-29 the sidebar is 3 expandable **modules**:
- **`แดชบอร์ด`** (every role) contains the 6 display pages. It is always open by default (`DASHBOARD_MODULE` in `openGroups`), because it is the most-used module and the only one a member sees. The name matches the client's own term ("Dashboard ใช้ …" in the equations docx). The pages are: เกี่ยวกับระบบ, ภาพรวมความเสี่ยง, แผนที่รายชุมชน, ปัจจัยความเสี่ยง, ผลกระทบและการฟื้นตัว, MCR2030 & KPI. The names come from the client's 5-page display spec image (`public/file/271069/f2c76ec6-….jpg`), without the number prefixes, plus MCR2030 & KPI.
- **`จัดการข้อมูล`** (admin/staff) contains นำเข้าข้อมูล.
- **`ตั้งค่าระบบ`** (admin) contains จัดการสมาชิก, จัดการชุมชน and จัดการเกณฑ์คะแนน. For staff/member it is an inert placeholder `<div>`.

A module is a `navItems` entry with a `children` array instead of an `href`. Its open state lives in `openGroups` (keyed by label), which auto-opens when the current page is one of its children. Add a new page as a child of the right module, not as a new top-level item.

`resources/js/components/admin/{DonutChart,TrendChart,StatCard,BarChart}.vue` are hand-rolled SVG charts with no charting library. They are currently unused after the reset. Reuse them for the rebuilt pages instead of adding Chart.js/ApexCharts/etc.

If a page needs a basemap, use the same three **Esri ArcGIS** tile services as `Welcome.vue` (`server.arcgisonline.com/ArcGIS/rest/services/{World_Imagery,World_Street_Map,Canvas/World_Light_Gray_Base}`, no API key). They used to be CartoDB (`basemaps.cartocdn.com`), but CartoDB started requiring an API key: unauthenticated requests still return HTTP 200 with a real-looking PNG, but every tile is watermarked "API KEY REQUIRED". A status-code check won't catch that, and neither will a screenshot glanced at rather than looked at closely; the project owner caught it by eye. Check the actual rendered pixels whenever a tile provider changes.

Custom toggle switches (`role="switch"` buttons) need an explicit `left-0.5` anchor on the thumb `<span>`, not just `top-0.5`. Omitting `left` was a real bug once: the thumb rendered outside the track.

**Role display labels**: `UserRole::label()` (PHP) and the `roleLabels` map duplicated in `Users.vue`/`AdminLayout.vue` (TS) both call the `member` role "บุคคลทั่วไป" (not "สมาชิก") — a deliberate rename; keep all three in sync if it changes again. The enum value itself is still `member`.

- **Storage:** weights are stored section → row → column, with `'ALL'` as the row for single-row "list" sections. A `null` schema cell means "not in this hazard's formula": it shows as "–", isn't editable and isn't stored.
- **Confirmed rules (owner, 2026-10-29):**
  - Only the numbers are editable. Formula structure is fixed in code. ×20, `C_HEVC = 1 + 0.8·C_RAW`, raw→0–5 bands and risk bands are not on this page.
  - Every row must sum to exactly 1 or the set can't be saved; the UI shows a live sum and the server re-checks. Each weight is 0–1 with ≤4 decimals.
  - E+V sum to 1. The C factor (default 0.16) is a multiplier and is **not** summed. It is editable with no 0.20 cap (owner choice); above 0.20 the UI shows only a non-blocking warning that high-capacity HEVC can go negative.
  - V_WARNING is a fixed 1.
  - Exactly one set is active, and `activate` deactivates the rest.
  - Admin locks/unlocks manually, and a locked set can't be updated (403).
  - Any set can be cloned; the clone starts inactive and unlocked.
  - Delete is allowed only when the set is neither active nor locked.
  - Set names are free text (e.g. "2569–2575"), not tied to a year.
  - Internal hazard keys are `FLOOD/FIRE/STORM/HEAT/PM25`, never "PM2.5" as a key; the display shows "PM2.5".

Original note: **HEVC data model** (source: an xlsx workbook the project owner supplied as a system-design template, not real data — see `data/` if it's ever committed, otherwise ask for it). The workbook defines a Hazard-Exposure-Vulnerability-Capacity risk-scoring methodology with these sheets, each mapping to a distinct part of this app rather than a 1:1 file import:
- `01_พจนานุกรม` (field dictionary) and `02_เกณฑ์คะแนน` (scoring weights/bands) are reference-only — never importable as row data. `02_เกณฑ์คะแนน`'s weights (e.g. Risk Driver = Hazard×0.35 + Exposure×0.25 + Vulnerability×0.40; Recovery = R1×0.25 + R2×0.25 + R3×0.20 + R4×0.15 + R5×0.15) are the actual HEVC calculation engine (implemented as `calculateHevc()`/`calculateRecoveryScore()` in `mockScoringCriteria.ts` — see "Shared mock-data modules" above) and should become application-level config/constants when the real backend is built, not a user-editable table (an accidental edit would silently reprice every historical risk score).
- `ภัยพิบัติรวม`'s **input** columns (population, household, per-person vulnerability counts, capacity baseline, recovery baseline, budget) belong to **`ข้อมูลชุมชน`** (one-time setup per community, not bulk import) — this is why that menu's field set traces back to this sheet. Its **output** columns (per-hazard HEVC rollup, dominant hazard, overall risk level, L&D totals) are computed by the system from the other sheets — never entered directly anywhere; the **`ภัยพิบัติรวม`** menu (see above) is where this computed rollup surfaces, not a form.
- `เหตุการณ์_LD` (event/Loss & Damage register) is the source of truth for individual incidents — confirmed by cross-checking real sample rows in the template (e.g. an event's `H_RAW` hazard-frequency count and its `L_EVENT_COUNT` documented-event count differ, proving the event register is a narrower independent log, not something derived from the per-hazard sheets). It has its own **`เหตุการณ์ L&D`** menu (per-event CRUD form, not xlsx import — see above) rather than `นำเข้าข้อมูล`, because events are logged one at a time as they happen.
- The 5 per-hazard sheets (`อุทกภัย`, `อัคคีภัย`, `วาตภัย`, `คลื่นความร้อน`, `PM 2.5`) map to **two** different menus depending on how the data arrives: bulk historical import goes through `นำเข้าข้อมูล` — **as a single combined "รายภัย" sheet differentiated by `HAZARD_CODE`, not 5 separate sheets** (all 5 shared the exact same column schema in the source workbook, confirmed by inspecting it directly, so consolidating them is a source-file reshape, not a schema change), and only the hazard-specific/BOTH-scope columns — H, E, V_system, hazard-specific equipment, R_mode/override, governance — never the SHARED-scope columns, which duplicate `ภัยพิบัติรวม`/`ข้อมูลชุมชน` data and should be joined live instead of re-imported; interactive one-off analysis/what-if goes through `รายภัย`.
