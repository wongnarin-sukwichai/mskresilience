# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ระบบบริหารข้อมูลความเสี่ยงและความเปราะบางของชุมชน (community risk & vulnerability data management system) for อำเภอเมือง, จังหวัดมหาสารคาม. A Laravel 12 + Inertia.js v2 + Vue 3 SPA, built on the official `laravel/vue-starter-kit`.

- Frontend: Vue 3 (`<script setup lang="ts">`), TypeScript, Tailwind CSS, shadcn-vue style UI components.
- Backend: Laravel 12, Inertia (server-driven routing, no separate REST/API layer for pages), Ziggy for route helpers in JS.
- Map: Leaflet (npm package, not CDN) — see `resources/js/pages/Welcome.vue` for the reference implementation (custom `L.divIcon` markers, per-risk `L.featureGroup` layers, tile-style toggle).
- Font: Anuphan everywhere (loaded via Google Fonts in `resources/views/app.blade.php`, set as `font-sans` in `tailwind.config.js` / `resources/css/app.css`). Icons: FontAwesome Free, installed as an npm package and imported in `resources/css/app.css` (not CDN).
- SPA behavior comes from Inertia itself — there is no `vue-router`. Navigation is server-routed (`routes/*.php` → `Inertia::render('PageName')`) but rendered client-side without full page reloads.

## Commands

```bash
composer install && npm install       # install deps
cp .env.example .env && php artisan key:generate

composer dev                          # run server + queue listener + pail logs + vite, concurrently (recommended for local dev)
php artisan serve                     # backend only
npm run dev                           # vite dev server only
npm run build                         # production build (also required before `npm run build:ssr`)

vendor/bin/pint                       # PHP formatting (run before committing PHP changes)
npm run format                        # Prettier (resources/)
npm run lint                          # ESLint --fix (resources/)

php artisan test                      # run all tests (or: vendor/bin/phpunit)
php artisan test --filter=test_name   # run a single test
php artisan test tests/Feature/DashboardTest.php
```

Tests are plain PHPUnit test classes under `tests/Feature` and `tests/Unit` (not Pest syntax, despite `tests/Pest.php` existing as an unused starter-kit leftover — `pestphp/pest-plugin` is not in `composer.json`). Tests run against in-memory SQLite (`phpunit.xml`); local dev DB is MySQL (`.env`, XAMPP).

CI (`.github/workflows/`) runs `vendor/bin/pint`, `npm run format`, `npm run lint` on push/PR (lint.yml), and `phpunit` + `npm run build` (tests.yml).

## Architecture

**Page routing**: `routes/web.php`, `routes/auth.php`, `routes/settings.php`, `routes/admin.php` define server routes that return `Inertia::render('PageName')`, resolving to `resources/js/pages/PageName.vue` (path relative to `pages/`, e.g. `Inertia::render('settings/Appearance')` → `resources/js/pages/settings/Appearance.vue`). There are no Blade views for actual pages — `resources/views/app.blade.php` is the single Inertia shell (fonts, `@vite`, `@inertia`), and `resources/views/example.blade.php` is a static HTML/JS mockup kept only as a design reference (it predates `Welcome.vue` and is not served by any route).

**`routes/admin.php`**: all `/dashboard`-family routes, under `['auth', 'verified']` plus per-route `role:` gating. Three tiers: dashboard viewing is `role:admin,staff,member` (open to everyone with an account); data import (`/data-import`), community data (`/community-data`), the disaster overview rollup (`/disaster-overview`), hazard analysis (`/hazard-analysis`), and the L&D register (`/events-ld`) are `role:admin,staff`; account management (`/users`) and scoring-criteria management (`/scoring-criteria`) are `role:admin` only — see "Roles" below. `App\Http\Controllers\Admin\*` and `resources/js/pages/admin/*.vue` are the corresponding namespace/folder — put new back-office pages there, gated the same way, rather than adding another top-level routes file. New admin pages: add the route here, add the nav entry in `AdminLayout.vue`'s `navItems` (role-conditionally if the route isn't open to all three roles — see how `จัดการสมาชิก`/`จัดการเกณฑ์คะแนน` are nested as admin-only children of the `ตั้งค่า` submenu, and `นำเข้าข้อมูล`/`ข้อมูลชุมชน`/`ภัยพิบัติรวม`/`รายภัย`/`เหตุการณ์ L&D` show flat for `admin`/`staff`), and use `AdminLayout` as the page's layout.

**Entry point**: `resources/js/app.ts` boots Inertia + Ziggy, resolves pages via `resolvePageComponent` globbing `./pages/**/*.vue`.

**Auth/session props**: `app/Http/Middleware/HandleInertiaRequests.php` shares props (e.g. `auth.user`) available in every page via `$page.props` / `usePage()`.

**Auth policy — self-registration is disabled.** `routes/auth.php` has no `register` routes (removed intentionally); `RegisteredUserController` and `pages/auth/Register.vue` still exist in the codebase but are unrouted/unlinked. Accounts are provisioned by an admin via `php artisan db:seed` (`database/seeders/DatabaseSeeder.php` seeds `test@example.com` / `password` as `member`, plus the real admin account below — replace/remove the test account before any real deployment). Login/logout/password-reset/email-verification all work normally through the standard Laravel session guard. `Welcome.vue`'s login modal (email+password, "ลืมรหัสผ่าน?" switches the same modal to a password-reset-request form) posts to these same routes via Inertia's `useForm` — it is a real auth client, not a mock. The modal's "เข้าระบบด้วยบัญชี @gmail" button is intentionally disabled (`disabled`, no handler) — Google/Socialite login was explicitly descoped, not forgotten; wiring it up needs `composer require laravel/socialite`, real Google OAuth credentials in `.env`, and a decision on whether Google sign-in may auto-create new accounts (it should probably match the same "no self-service account creation" policy as password login, but that's a product decision to confirm, not assume).

**Roles**: `App\Enums\UserRole` (`admin` | `staff` | `member`), stored as a plain `string` column on `users` (`role`, default `member`), cast to the enum on the `User` model. Route-level gating uses the `role:` middleware alias (`App\Http\Middleware\EnsureUserHasRole`, registered in `bootstrap/app.php`) — e.g. `Route::...->middleware(['auth', 'verified', 'role:admin,staff'])`. `User::canAccessAdminPanel()` is the **single source of truth** for "can this user reach `/dashboard`" (all three roles as of the current permission model — see the per-menu breakdown below) — both `AuthenticatedSessionController::store()` (post-login redirect) and `AppServiceProvider::boot()` (`RedirectIfAuthenticated::redirectUsing(...)`, for the `guest` middleware's "already logged in" redirect on `/login`) call it, and must keep calling it rather than re-deriving the role check inline. **This split was a real bug once**: Laravel's default `guest`-middleware redirect always targets `route('dashboard')` if it exists, with no regard for role — an already-logged-in member hitting `/login` (e.g. to switch accounts) got bounced straight into a 403 with their new credentials never even processed, and no visible way to log out to recover, since `Welcome.vue`'s header didn't show auth state at all. Both are now fixed (role-aware redirect + `Welcome.vue` shows a user chip/logout when `auth.user` is set) — if you add another role-gated route, ask whether the same two spots need updating. Seeded accounts: `test@example.com` / `password` (member), `wongnarin.s@msu.ac.th` / `w123` (admin, real credentials requested by the project owner — rotate before production).

**Per-menu permission matrix** (current product decision, distinct from `canAccessAdminPanel()` which only gates the dashboard itself): `admin` — every menu, including the `ตั้งค่า` submenu (`จัดการสมาชิก`, `จัดการเกณฑ์คะแนน`). `staff` — `นำเข้าข้อมูล`, `ข้อมูลชุมชน`, `ภัยพิบัติรวม`, `รายภัย`, `เหตุการณ์ L&D`; no access to anything under `ตั้งค่า`. `member` — dashboard-family menus only; blocked from all of the above. `AdminLayout.vue`'s `navItems` computed hides menu entries the current user can't reach (rather than showing a dead link that 403s); `routes/admin.php`'s `role:` middleware is the actual enforcement — keep both in sync when adding a role-restricted route. `ข้อมูลชุมชน` replaced the old `จัดการชุมชน`, which used to live admin-only under `ตั้งค่า` — the replacement page moved back to the flat admin+staff group per product decision (see the `ข้อมูลชุมชน` bullet below).

**User management** (`/users`, admin-only): `App\Http\Controllers\Admin\UserManagementController` + `resources/js/pages/admin/Users.vue`. Since self-registration is disabled, this is the only way new accounts get created — plain CRUD (no pagination yet; revisit if the user list grows large). `guardLastAdmin()` in the controller blocks deleting or demoting the system's sole remaining admin (returns a 403 with a Thai message); the destroy action separately blocks deleting your own account. If you touch this controller, keep both guards — they protect against different lockout scenarios (see the tests in `tests/Feature/Admin/UserManagementTest.php` for why the "delete" guard and "demote" guard can't be collapsed into one check: destroy always requires the actor to already be an admin, so "delete the last admin" and "delete yourself" overlap in practice, but demotion doesn't have that overlap).

**Locale**: `APP_LOCALE=th` (fallback `en`) — `lang/th/auth.php` translates the auth-guard error strings (`auth.failed`, `auth.throttle`) since the whole UI is Thai. Only that one file exists under `lang/th/`; other framework validation/auth strings still fall back to English if triggered. Extend `lang/th/*.php` as more server-side user-facing strings come up rather than leaving them in English.

**Layouts**: `resources/js/layouts/` (`AppLayout`, `AppHeaderLayout`, `AppSidebarLayout`, `AuthLayout` and variants) wrap authenticated/settings pages. Full-screen/standalone pages like `Welcome.vue` intentionally render with no layout wrapper.

**UI components**: `resources/js/components/ui/*` are shadcn-vue primitives (Button, Dialog, Sidebar, etc.) — see `components.json` for the shadcn-vue config (aliases, Tailwind base color `neutral`). Don't hand-roll a component if an equivalent already exists there.

**Map pages** (pattern established in `Welcome.vue`): keep the Leaflet `L.Map` instance and layer/tile-layer objects as plain module-scope variables (`let`), *not* `ref`/`reactive` — Leaflet manages its own internal mutable state and wrapping it in Vue's reactivity is unnecessary and can misbehave. Always `map.remove()` in `onUnmounted` since Inertia navigation mounts/unmounts page components without a full browser reload, and Leaflet throws if you re-`L.map()` the same container without cleanup.

**Body-level page styles**: pages needing full-viewport/no-scroll layouts (like `Welcome.vue`) toggle a class on `document.body` in `onMounted`/`onUnmounted` rather than setting it globally in CSS, since multiple Inertia pages share one `<body>` across navigations.

**Sourcing real geodata** (pattern established in `Welcome.vue`): don't invent coordinates/boundaries and present them as real. Administrative boundary polygons (province/district/municipality) can be pulled live and legitimately via Nominatim (`https://nominatim.openstreetmap.org/search?...&format=geojson&polygon_geojson=1`, © OpenStreetMap contributors, ODbL — attribute it). Official place/community names and counts for this municipality come from `data.mkm.go.th` (เทศบาลเมืองมหาสารคาม's own open-data portal), not Wikipedia (which was found outdated: 30 vs. the current official 32 ชุมชน). Sub-municipal "ชุมชน"-level boundaries are not published anywhere as open geodata and the project owner has requested a real shapefile — when real names/boundary exist but per-point coordinates or per-community area polygons don't, generate an approximation from what real data *does* exist (see the Voronoi-zone note below) and say so both in a code comment and somewhere user-visible, rather than fabricating precision that doesn't exist.

**Shared community/boundary data**: `resources/js/data/mahasarakham.ts` is the single source of truth for `MAP_CENTER`, `MUNICIPALITY_BOUNDARY`, `riskColors`, `riskNameTH`, and the 32-entry `communities` array (see the "Sourcing real geodata" note above for what's real vs. placeholder in there). Both `Welcome.vue` and the admin `Dashboard.vue` map import from it — **don't re-declare this data in a new page; import it**, so the ~150-point boundary polygon and community list stay in exactly one place.

**Placeholder community-area zones** (`resources/js/data/communityZones.ts`, used by both `Welcome.vue`'s public map and `Dashboard.vue`'s risk map): while waiting on the real shapefile, area-style zone polygons are generated at runtime — a Voronoi diagram (`d3-delaunay`) over the 32 community center points, each cell clipped to the real `MUNICIPALITY_BOUNDARY` via `polygon-clipping` (needed because the boundary is concave; Sutherland–Hodgman-style clipping only works against a convex clip region). This tiles the real municipal boundary with no gaps/overlaps for a convincing area-shaded map, but cell edges are a mathematical artifact of point layout, not surveyed lines — both pages show a visible amber disclaimer (near the map heading on the dashboard, a floating bottom-center chip on the public homepage) and repeat it in every zone's popup, not just a code comment, because this one renders as filled area coverage users could easily mistake for real boundaries at a glance. `Welcome.vue` colors zones by hazard type (`riskColors[com.activeRisk]`, matching that page's existing legend/filter model) while `Dashboard.vue` colors by computed HEVC risk level (`riskLevelMeta`) — same zone shapes, different color semantics per page, so don't assume one page's zone color scheme when touching the other. **When the real shapefile arrives, delete this file's generation logic and hardcode the real ring coordinates instead** (same shape as `MUNICIPALITY_BOUNDARY`) — don't leave the Voronoi approximation running silently alongside real data. `polygon-clipping`'s ESM build only has a default export despite its `.d.ts` declaring named exports (`import { intersection }` type-checks but is `undefined` at runtime) — import the default, and `import type * as` separately for its `Ring`/`Polygon`/`Pair` types (a default import can't be used as a type qualifier); see the comment in `communityZones.ts` if this needs revisiting.

**Fading Leaflet filter toggles** (`resources/js/lib/leafletFade.ts`, used by both `Welcome.vue`'s risk-type radio filter and `Dashboard.vue`'s hazard-toggle filter): Leaflet has no built-in transition for vector layers (`L.FeatureGroup`/`L.Polygon`/`L.Marker`) the way raster tile layers do, so `fadeInGroup()`/`fadeOutGroup()` reach into each layer's DOM element (`getElement()` where public, the private-but-stable `_path` for `Path`-based layers using the default SVG renderer) and drive a plain CSS `opacity` transition before actually calling `map.removeLayer()`. Reuse these two functions for any new toggleable map layer rather than reintroducing instant add/remove or a second animation implementation.

**Admin panel** (`resources/js/layouts/AdminLayout.vue` + `resources/js/pages/Dashboard.vue`, dashboard gated `role:admin,staff,member`): a bespoke dark-sidebar shell (not the shadcn `AppSidebarLayout` — different visual language, built custom like `Welcome.vue`). `AdminLayout.vue`'s `navItems` mixes flat real `Link`s ("แดชบอร์ด", "นำเข้าข้อมูล", "ข้อมูลชุมชน", "ภัยพิบัติรวม", "รายภัย", "เหตุการณ์ L&D", role-gated per the permission matrix above) with roadmap placeholders for pages that don't exist yet (จุดเสี่ยง, ชั้นข้อมูลแผนที่, หลักฐาน, ค่าล่าสุด, แจ้งเตือน, รายงาน) — the placeholders intentionally render as inert `<div>`s (not `<Link>`/`<a>`), not broken links, per product decision (keep the whole planned menu visible as a roadmap rather than hiding unbuilt pages entirely; the placeholder list is deliberately kept in sync with the 7-menu sidebar in the original 01.png reference — ภาพรวม/แผนที่ความเสี่ยง/ข้อมูลชุมชน/รายภัย/เหตุการณ์ L&D/หลักฐาน/รายงาน — so nothing from that reference silently gets dropped; ข้อมูลชุมชน has since graduated from placeholder to a real built page). `ตั้งค่า` (settings) is the one exception to the flat-list pattern: for `admin` it's a real *expandable* item (a `navItems` entry with a `children` array instead of an `href` — click toggles the `settingsOpen` ref, which also auto-opens if the current page matches a child route) nesting `จัดการสมาชิก` and `จัดการเกณฑ์คะแนน` (both `role:admin` in `routes/admin.php`; community management used to be a third child here as `จัดการชุมชน` but was replaced by the flat `ข้อมูลชุมชน` item — see below); for `staff`/`member` it stays the same inert roadmap placeholder (`{ label, icon }`, no `children`, no `href`) it always was — don't let it disappear for them, since as a general "system settings" concept it may grow content beyond just these 2 admin items later. When building one of the flat roadmap placeholders, promote its nav entry to `{ label, icon, href: route('...') }` (role-conditionally) rather than adding a parallel nav system; when adding another admin-only settings page, add it as a new entry in `ตั้งค่า`'s `children` array instead of a new top-level item. `resources/js/components/admin/{DonutChart,TrendChart,StatCard,BarChart}.vue` are hand-rolled SVG charts (no charting library dependency) — reuse them for future admin pages instead of adding Chart.js/ApexCharts/etc. **Everything on the dashboard except the stat card "จำนวนชุมชนทั้งหมด" (real, from `communities.length`) and the map's community list/coordinates is mock data** — there's no `hazard_assessments` or `scoring_criteria` table yet (see the HEVC data model note below); "เหตุการณ์สะสม" and "เหตุการณ์ล่าสุด" *do* read the real shared `events` store (see "Shared mock-data modules" below), so those two are live within a browser session even though nothing is backed by a database yet. When a real backend exists, replace the remaining mock arrays in `Dashboard.vue` with real Inertia props from a controller; don't leave mock data silently stale once a real source exists. The risk map supports the same 3-way tile-style toggle (ดาวเทียม/แผนที่สี/ขาวดำ) as `Welcome.vue`, using the same three tile URLs — keep both in sync if the tile provider ever changes. The filter panel's "เลือกชุมชน" dropdown and "ช่วงวันที่ข้อมูล" date inputs are real, working controls (bound to `selectedCommunityId`/`filterStartDate`/`filterEndDate`) but intentionally not wired to actually filter the map/data yet — don't assume selecting them does anything beyond updating their own display state. The custom toggle switches (`role="switch"` buttons) need an explicit `left-0.5` anchor on the thumb `<span>`, not just `top-0.5` — omitting `left` was a real bug once (the thumb's un-transformed position fell back to the browser's "static position" fallback, which rendered it entirely outside the track, off to the right).

**Role display labels**: `UserRole::label()` (PHP) and the `roleLabels` map duplicated in `Users.vue`/`AdminLayout.vue` (TS) both call the `member` role "บุคคลทั่วไป" (not "สมาชิก") — a deliberate rename; keep all three in sync if it changes again. The enum value itself is still `member`.

**Shared mock-data modules** (`resources/js/data/hazardMeta.ts`, `mockScoringCriteria.ts`, `mockEvents.ts`): the mock-data equivalent of a database — each exports a **module-level `ref`** (not a local `ref` re-created per component), so every page that imports it reads/writes the *same* in-memory store for the lifetime of a browser session (resets on reload, which is fine/expected for mock data). This is what makes the mock pages actually cross-reference each other instead of being disconnected islands:
- `hazardMeta.ts` — `hazardOrder`, `hazardShortLabel` (short labels for tight spaces — `riskNameTH` in `mahasarakham.ts` is long-form display copy for map popups/legends and overflows filter panels/table cells; reach for `hazardShortLabel` anywhere space-constrained instead), `hazardIcons`, `hazardBadgeClass`, `riskLevelMeta`/`riskLevelFromScore` (the `<25`/`25–<50`/`50–<75`/`≥75` bands from `02_เกณฑ์คะแนน`), and `seededValue()` (the shared deterministic-pseudo-random helper — don't reimplement a local `Math.sin()` seed function per page, import this one).
- `mockScoringCriteria.ts` — `criteriaList` (the shared เกณฑ์คะแนน store `ScoringCriteria.vue` performs CRUD against), `weightGroups`/`baselineWeights()`, and the calculation engine: `calculateHevc(weights, {hazard, exposure, vulnerability, capacity})` and `calculateRecoveryScore(weights, {r1..r5})`. **`calculateHevc`'s formula is a reconstruction, not a confirmed-correct one** — the source workbook's cells exposed structure and weights but not the literal Excel formula text, so the Risk-Driver-weighted-H/E/V dampened by Capacity-as-mitigation logic in there is a reasonable guess flagged for the data provider to confirm when this mock is reviewed, not something to treat as settled.
- `mockEvents.ts` — `events` (the shared เหตุการณ์_LD store both `Dashboard.vue`'s "เหตุการณ์ล่าสุด" preview and `EventsLD.vue`'s full register read from) plus derived-field helpers (`communityName()`, `isMultiHazard()`, `eventRecoveryScore()`, `nextEventId()`) for the 3 fields that must never be stored (see the เหตุการณ์_LD bullet below).

**`ข้อมูลชุมชน`** (`/community-data`, `role:admin,staff`, flat item in `AdminLayout.vue` right after `นำเข้าข้อมูล` — replaces the old admin-only `จัดการชุมชน` (deleted, was nested under `ตั้งค่า`), `resources/js/pages/admin/CommunityData.vue`): matches a `06.png` UI reference the project owner supplied. Unlike `จัดการชุมชน`, this is a **read-oriented registry/profile view, not a CRUD form** — no create/edit/delete modal, the bottom action buttons (บันทึกฉบับร่าง/ดาวน์โหลดข้อมูล/บันทึกข้อมูลชุมชน) are decorative like other mock action buttons in this app. Fully mock, derived deterministically from the real 32-community list in `mahasarakham.ts` via `seededValue()` (no `communities`/`hazard_assessments` table yet). Covers the **full** ภัยพิบัติรวม "SHARED-scope input" field set (see the HEVC data model note below) rather than จัดการชุมชน's small 6-field starter subset: Meta (POPULATION/HOUSEHOLDS/AREA_KM2/TAMBON/AMPHOE/PROVINCE), the 4 Vulnerability groups (V_ELDERLY/V_CHILD/V_BEDRIDDEN_DISABLED/V_LOW_INCOME, each COUNT), the 4 Capacity shared scores plus C_TOTAL_SHARED_SCORE, R1_SHARED–R5_SHARED plus R_SHARED_SCORE (via the shared `calculateRecoveryScore()` against the default เกณฑ์คะแนน, not invented separately), and Data Governance (SOURCE/EVIDENCE/DATA_DATE/RESPONSIBLE_AGENCY/VERIFICATION_STATUS/DATA_QUALITY) — field names mirror the real source workbook's columns 1:1. Layout: a 7-tile stat row (totals across all 32 communities), a ทะเบียนชุมชน table (10 rows/page) whose row click sets the selected community, a โปรไฟล์ชุมชน card (field grid + VERIFICATION_STATUS/DATA_QUALITY chips + a small non-interactive Leaflet locator map — module-scope `let` + `map.remove()` in `onUnmounted`, same "Map pages" pattern as elsewhere, recentered via a `watch` on the selected community rather than destroyed/recreated), a กลุ่มเปราะบางของชุมชน `DonutChart` (the 4 vulnerability groups plus a residual "ประชากรกลุ่มอื่น" segment so legend percentages read as a genuine share of that community's population, not just a share of the 4 named groups), a สรุป Capacity และ Recovery card (Capacity as progress bars, Recovery as a checkmark list), and a โครงสร้างข้อมูลในเมนูข้อมูลชุมชน field-dictionary reference grid (5 groups, same static-reference pattern as เหตุการณ์ L&D's กรอบข้อมูล row). The vulnerability-share formulas intentionally keep `seededValue()`'s divisor large (e.g. `/2000`, not `/400`) — an early version divided by too little and produced elderly shares over 35%, an unrealistic number that was caught by screenshotting the page, not by reading the code.

**`นำเข้าข้อมูล`** (`/data-import`, `role:admin,staff`, `resources/js/pages/admin/DataImport.vue`): a single-page flow (redesigned from an earlier 5-step click-through wizard, per product decision — all steps' cards now live on one page instead of one-at-a-time panels behind ถัดไป/ย้อนกลับ buttons), also fully mock — the uploaded file's name/size are read for real via the browser File API, but nothing is parsed or persisted. On load, only the อัปโหลดไฟล์ card is visible and the timeline shows step 1. Selecting/dropping a file sets `isUploading` (spinner shown in that card) for a simulated ~1s delay, then `scheduleReveal()` cascades `revealedStep` 2→5 on staggered timers, each threshold `v-if`-revealing the next card(s) (แผ่นงานที่พบในไฟล์ → ผลตรวจสอบไฟล์ + ตัวอย่างข้อมูลก่อนนำเข้า → จับคู่ฟิลด์ข้อมูล → the ยืนยันนำเข้าข้อมูล action bar) wrapped in a `<Transition name="fade-rise">` — the timeline's highlighted step is literally `revealedStep`, so it always matches whatever's currently rendered, not a separately-tracked variable. **The 5 per-hazard sheets are combined into a single "รายภัย" data sheet, differentiated row-by-row via `HAZARD_CODE`** (a later product decision, confirmed feasible against the real source workbook: all 5 hazard sheets already share the exact same ~139-column schema, and `HAZARD_CODE`/`HAZARD_NAME` are already row-level fields in every one of them, so this is a wide→long consolidation of the source file, not a new field) — the `แผ่นงานที่พบในไฟล์` card is now purely informational (the workbook has just 1 data sheet + 3 reference sheets, nothing to pick there), and the `hazardTypes` checkbox list (which HAZARD_CODE groups to import this round) is what the old per-sheet checkboxes used to be. The ผลตรวจสอบไฟล์ card's error/warn states are computed live from which hazard types are checked (e.g. checking the 0-row PM 2.5 hazard type trips a real blocking error and disables the ยืนยันนำเข้าข้อมูล button), not hardcoded — **don't hardcode an unconditional `error` status in `validationChecks`**, it was a real bug here once. Since cards no longer gate each other behind "next", hazard-type checkboxes stay editable after being revealed and validation/mapping recompute reactively — there's no per-step lock-in. `removeFile()`/changing the file resets `revealedStep` back to 1 and clears the pending reveal timers (`clearRevealTimers()`, also called in `onUnmounted` — Inertia navigation unmounts without a full reload, so a stale `setTimeout` from a previous visit must not fire against a torn-down component).

**`ภัยพิบัติรวม`** (`/disaster-overview`, `role:admin,staff`, `resources/js/pages/admin/DisasterOverview.vue`): the per-community rollup view for the `ภัยพิบัติรวม` sheet's **output** columns (see the HEVC data model note below) — built to match a `03.png` UI reference the project owner supplied. Fully mock, derived deterministically from the real 32-community list in `mahasarakham.ts` via `seededValue()`: population/households mirror `ข้อมูลชุมชน`'s Meta group (a separate mock island there, not re-imported — the two won't show identical numbers, only the same realistic shape), and ~1/3 of communities are seeded `assessed: false` ("ยังไม่ประเมิน" — no per-hazard sheet imported yet) to demonstrate data-completeness tracking; `RECOVERY_AVG`/`L3_DAMAGE_TOTAL_THB` come from the เหตุการณ์ L&D register instead of the hazard assessment, so they stay populated even for unassessed communities, matching the real sheet's independent column groups. The main table/zone card has a view toggle (ตาราง ⇄ ผังพื้นที่, a product decision from the same discussion that spawned this page): the ผังพื้นที่ view reuses `communityZones.ts`'s Voronoi-clipped zone polygons over a Leaflet map. **This briefly shipped without a `TileLayer` (a product decision at the time), then got a basemap added back** the same day after the project owner tried it and asked for one — it now uses the same light/gray CartoDB tile URL as `Dashboard.vue`'s "ขาวดำ" style (a muted basemap so the risk-colored zone fills stay the visual focus, standard choropleth practice), not the full satellite/color/gray 3-way toggle Dashboard has. If a similar "just the shapes, no basemap" need comes up again elsewhere, that's a real option Leaflet supports (skip the `L.tileLayer().addTo(map)` call) — just don't assume it's still true for this page. That map is mounted/torn down on toggle (not kept alive off-screen) via a `viewMode` watcher calling `initZoneMap()`/`destroyZoneMap()`, following the same module-scope-`let`-plus-`map.remove()` pattern as the "Map pages" note above. The 8-tile stat row is a page-local compact tile (`statTiles`), not `components/admin/StatCard.vue` — StatCard's fixed padding/icon size/`text-2xl` value are sized for the 3-4-per-row layouts other pages use it in, and don't have a compact variant, so fitting 8 stats in one row needed its own smaller markup rather than wrapper classes fighting StatCard's internals. **`จัดการเกณฑ์คะแนน`** (`/scoring-criteria`, `role:admin` only, `resources/js/pages/admin/ScoringCriteria.vue`): CRUD for versioned scoring-criteria sets, reading/writing the shared `criteriaList` store (see "Shared mock-data modules" above) — no longer an isolated island, `รายภัย` and `เหตุการณ์ L&D` both consume it. **`รายภัย`** (`/hazard-analysis`, `role:admin,staff`, `resources/js/pages/admin/HazardAnalysis.vue`): the H-E-V-C-Recovery analysis workbench — matches "แผ่นรายภัย" in the source workbook, **not** `เหตุการณ์ L&D` (a stakeholder request initially described this workbench under the "เหตุการณ์ L&D" name, but cross-checking `00_คำแนะนำ`'s function/usage columns showed the editable-inputs behavior belongs to แผ่นรายภัย, while เหตุการณ์_LD's documented function is pure recording). Redesigned per a `04 (2).png` UI reference the project owner supplied into a single unified page — the old mode toggle is gone; hazard is picked via 5 tab buttons at the top (one per per-hazard sheet), community via the "เลือกชุมชน" filter, and the bulk table plus single-community breakdown render together, live (no separate "คำนวณ" trigger — everything is a reactive `computed`; the bottom "อัปเดตผลคำนวณ" button is decorative, matching other mock action buttons in this app). The single-community breakdown exposes the *full* field-dictionary detail from the source workbook's per-hazard sheets, not just the four H/E/V/C scores: Hazard & Exposure (H_RAW, H_SCORE, E_METHOD/NUMERATOR/DENOMINATOR/PERCENT, E_SCORE), Vulnerability (V_WARNING_SHARED_SCORE, V_WARNING_HAZARD_STATUS, V_INFRA_GAP_COUNT/SCORE, V_SYSTEM_SCORE, V_TOTAL_SCORE), Capacity (C_SOCIAL/PHYSICAL/OPERATIONAL/EVAC_NETWORK_EFFECTIVE, C_TOTAL_SCORE), Recovery (R1-R5, RECOVERY_SCORE), and Loss & Damage / Governance (L_EVENT_COUNT, L1_HOUSES_DAMAGED, L3_DAMAGE_VALUE_THB, SOURCE, EVIDENCE, DATA_DATE, VERIFICATION_STATUS) — all deterministic via `seededValue()`, following the same per-community × per-hazard seed-offset pattern the old baseline generators used. **H/E/V/C are always computed from baseline/system data with no manual override** (the real workbook's intent: these come from GIS/census/system feeds) — only Recovery (R1-R5) keeps a USE_SHARED/OVERRIDE toggle, since Recovery is human-observed per event and may need correcting; this is a deliberate simplification versus the reference design, which showed toggle-like controls on every group. **HEVC data model** (source: an xlsx workbook the project owner supplied as a system-design template, not real data — see `data/` if it's ever committed, otherwise ask for it). The workbook defines a Hazard-Exposure-Vulnerability-Capacity risk-scoring methodology with these sheets, each mapping to a distinct part of this app rather than a 1:1 file import:
- `01_พจนานุกรม` (field dictionary) and `02_เกณฑ์คะแนน` (scoring weights/bands) are reference-only — never importable as row data. `02_เกณฑ์คะแนน`'s weights (e.g. Risk Driver = Hazard×0.35 + Exposure×0.25 + Vulnerability×0.40; Recovery = R1×0.25 + R2×0.25 + R3×0.20 + R4×0.15 + R5×0.15) are the actual HEVC calculation engine (implemented as `calculateHevc()`/`calculateRecoveryScore()` in `mockScoringCriteria.ts` — see "Shared mock-data modules" above) and should become application-level config/constants when the real backend is built, not a user-editable table (an accidental edit would silently reprice every historical risk score).
- `ภัยพิบัติรวม`'s **input** columns (population, household, per-person vulnerability counts, capacity baseline, recovery baseline, budget) belong to **`ข้อมูลชุมชน`** (one-time setup per community, not bulk import) — this is why that menu's field set traces back to this sheet. Its **output** columns (per-hazard HEVC rollup, dominant hazard, overall risk level, L&D totals) are computed by the system from the other sheets — never entered directly anywhere; the **`ภัยพิบัติรวม`** menu (see above) is where this computed rollup surfaces, not a form.
- `เหตุการณ์_LD` (event/Loss & Damage register) is the source of truth for individual incidents — confirmed by cross-checking real sample rows in the template (e.g. an event's `H_RAW` hazard-frequency count and its `L_EVENT_COUNT` documented-event count differ, proving the event register is a narrower independent log, not something derived from the per-hazard sheets). It has its own **`เหตุการณ์ L&D`** menu (per-event CRUD form, not xlsx import — see above) rather than `นำเข้าข้อมูล`, because events are logged one at a time as they happen.
- The 5 per-hazard sheets (`อุทกภัย`, `อัคคีภัย`, `วาตภัย`, `คลื่นความร้อน`, `PM 2.5`) map to **two** different menus depending on how the data arrives: bulk historical import goes through `นำเข้าข้อมูล` — **as a single combined "รายภัย" sheet differentiated by `HAZARD_CODE`, not 5 separate sheets** (all 5 shared the exact same column schema in the source workbook, confirmed by inspecting it directly, so consolidating them is a source-file reshape, not a schema change), and only the hazard-specific/BOTH-scope columns — H, E, V_system, hazard-specific equipment, R_mode/override, governance — never the SHARED-scope columns, which duplicate `ภัยพิบัติรวม`/`ข้อมูลชุมชน` data and should be joined live instead of re-imported; interactive one-off analysis/what-if goes through `รายภัย`.
